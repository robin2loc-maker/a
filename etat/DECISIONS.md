# Décisions prises en autonomie

Format : **Décision** — raison — alternative écartée — à valider par l'humain ? (oui/non)

- **Parcours par défaut : paiement, puis questionnaire, puis résultats** (`FUNNEL_MODE=pay_first`) — cohérent avec la page de vente (« Cliquez sur le bouton, répondez aux questions, et recevez ses trois pistes ») — le questionnaire avant paiement est prévu en bonus (B1) pour un test A/B — à valider : oui.
- **Versions : Next.js 16.4.5 (Turbopack, gabarit officiel `create-next-app`), React 19.3, Tailwind 4.3 via `@tailwindcss/turbopack`, ESLint 9, TypeScript 6.0.3** — TypeScript 7 est sorti mais `typescript-eslint` exige TypeScript < 6.1 ; ESLint 9 est la version du gabarit Next — TypeScript 7 et ESLint 10 écartés pour l'instant — à valider : non.
- **`cacheComponents` désactivé** (le gabarit Next 16.4 l'active) — le produit est fait de pages à jeton dynamiques (`/resultats/[token]`…) ; ce mode impose des `Suspense` partout et des conventions encore peu connues — alternative écartée : garder le gabarit tel quel — à valider : non.
- **Aucune police chargée depuis Google Fonts pour l'instant (pile système)** — `next/font/google` télécharge au build, or le build doit marcher sans réseau fiable ; la police définitive (fichier local via `next/font/local`) relève de la conception des écrans — à valider : non.
- **Textes : modules TypeScript dans `content/`, typographie appliquée au rendu par `typographier()` (src/lib/typographie.ts)** — typés, faciles à modifier, lisibles par le test des tics d'IA (tests/contenu.test.ts) — alternative écartée : JSON ou Markdown (pas de typage, pas de commentaires) — à valider : non.
- **Typographie : espace fine insécable (U+202F) avant ; ! ? et dans les guillemets, insécable (U+00A0) avant les deux-points et après un nombre, apostrophe courbe (’)** — usage de l'Imprimerie nationale, rendu propre sur mobile — alternative écartée : insécable ordinaire partout — à valider : non. Conséquence pour les tests E2E : passer un texte de `content/` par `typographie()` avant de le chercher dans la page.
- **Liste des tics d'IA dans `src/lib/tics-ia.ts`, synchronisée avec docs/STYLE.md par un test** (chaque terme cité entre guillemets dans la ligne « Tics d'IA » doit être détecté ; « passion » couvre passionné, passionnant… ; « s'épanouir » couvre épanoui, épanouissement) — alternative écartée : lire STYLE.md à l'exécution (fragile) — à valider : non.
- **Base locale : rôle `bilan`, mot de passe `bilan`, base `bilan3pistes`** (`postgres://bilan:bilan@localhost:5432/bilan3pistes`, indiquée dans `.env.example` ; depuis 0.3, drizzle.config.ts n'a plus d'URL par défaut) — l'accès `postgres` en TCP exige un mot de passe ; identifiants de développement local uniquement, pas un secret — à valider : non. Première migration : table technique `app_meta` (clé, valeur), les tables du produit viendront avec leurs tâches. Connexion paresseuse (`getDb()`), donc le build n'exige ni PostgreSQL ni variable.
- **E2E sur un build de production (`next build && next start`, port 3100), un seul projet mobile 390 × 844** — plus proche du réel que `next dev` ; Chrome préinstallé via `CHROME_PATH` — à valider : non.
- **`npm run screenshots` lance lui-même `next start` (port 3200) si aucun serveur ne répond**, captures pleine page par défaut (`--ecran` pour l'écran seul), nom `chemin=nom` facultatif — réutilisable par tous les sous-agents sans préparation — à valider : non.
- **Le workflow CI lance seulement `npm run check`** (pas l'E2E, qui demanderait un navigateur dans GitHub Actions) — conforme à CLAUDE.md §7 — à valider : non.
- **Configuration : un seul module (`src/lib/config.ts`), seul lecteur de `process.env`. Variable absente ou vide : repli sur la brique de démo ; variable présente mais mal formée : le serveur refuse de démarrer en nommant la variable** — basculer en silence sur le paiement simulé parce qu'une clé est mal recopiée serait pire qu'un arrêt — alternative écartée : ignorer les valeurs invalides — à valider : non.
- **Garde-fous croisés : `STRIPE_WEBHOOK_SECRET` obligatoire avec `STRIPE_SECRET_KEY` ; `SIGNING_SECRET` obligatoire avec une clé `sk_live_` ; pixel obligatoire avec `META_CAPI_TOKEN`** — sans webhook, un paiement réel ne déclencherait aucun bilan ; avec la clé de démo publique, n'importe qui forgerait des liens — alternative écartée : avertissement dans le journal — à valider : non.
- **Noms des variables non fixés par la SPEC : `SIGNING_SECRET` (32 caractères min.), `APP_URL` (défaut `http://localhost:3000`), `STRIPE_PRICE_BILAN` et `STRIPE_PRICE_OPTION` (facultatifs), `META_TEST_EVENT_CODE`** — les montants 27 € et 17 € restent dans le code, car la page de vente les écrit en toutes lettres : une variable de prix pourrait les désynchroniser ; les identifiants de prix Stripe servent seulement aux rapports Stripe — alternative écartée : montants en variables — à valider : non.
- **Valeurs par défaut : `SUPPORT_EMAIL` = support@touslesmetiers.com, `EMAIL_FROM` = « touslesmetiers.com <bilan@touslesmetiers.com> »** — l'email de garantie doit toujours s'afficher — à valider : **oui** (ces adresses doivent exister, le domaine doit être validé dans Resend).
- **Sans `ADMIN_PASSWORD` (12 caractères min.), `/admin` reste fermé**, même en démo — pas de porte ouverte par défaut — alternative écartée : mot de passe de démo — à valider : non.
- **« Mode démo » = au moins une brique de démo active (`config().demo.actif`)**, avec un drapeau par brique (paiement simulé, stockage dans l'URL, LLM désactivé, emails en console, clé de signature de démo) ; le serveur les résume au démarrage (`src/instrumentation.ts`), sans secret — à valider : non.
- **Jeton du mode démo : `1.<JSON compressé deflate, base64url>.<HMAC-SHA256 tronqué à 128 bits>`** (`src/lib/jeton-signe.ts`), signé mais **non chiffré** : le détenteur du lien peut lire les réponses, comme il peut lire la page de résultats ; plafonds 8 000 caractères et 64 Ko décompressés ; un UUID aléatoire dans la charge rend deux bilans aux réponses identiques impossibles à confondre — alternative écartée : chiffrement AES-GCM (jeton plus long, aucun gain réel pour le détenteur légitime) — à valider : non.
- **Stockage : interface `StockageBilans` (créer, enregistrer, lire), deux implémentations (PostgreSQL, table `bilans` avec jeton aléatoire de 128 bits distinct de l'UUID interne ; URL signée, nouveau jeton à chaque enregistrement). Seules les réponses sont stockées, les résultats sont recalculés** — conséquence pour la phase 3 : en mode URL, aucun texte LLM ne peut être conservé, donc ce mode reste sur les gabarits (le LLM n'est appelé, et son texte mis en cache, qu'avec une base) — alternative écartée : rappeler le LLM à chaque visite (coûteux, non reproductible) — à valider : non.
- **ROME : export complet `api.francetravail.fr/api-nomenclatureemploi/v1/open-data/json` (ROME 4.0 v62, octobre 2026), lu en ISO-8859-15**, plutôt que les arborescences XLSX — il contient tout (fiches, contextes, savoir-être, compétences, accès, mobilités) en un fichier ; le CSV du même export sert pour RIASEC et les étiquettes officielles — alternative écartée : les 8 XLSX d'arborescences — à valider : non.
- **Outil de téléchargement en Python (`scripts/data/telecharger.py`) appuyé sur curl**, 12 essais par défaut (40 pour l'ESR), 2 requêtes/s max par hôte, refus des pages HTML anti-robot — curl passe le proxy et son CA sans réglage ; Python est déjà prévu pour les scripts de données — alternative écartée : TypeScript avec fetch (proxy à configurer) — à valider : non.
- **Parcoursup : cartographie 2026 (formations proposées) comme base, vœux 2025 en enrichissement facultatif** — la cartographie couvre l'offre en cours (25 793 formations, 11 251 en apprentissage) ; les vœux 2026 ne sont pas encore publiés — à valider : non.
- **ROME → ISCO-08 par la table EURES ESCO ↔ ROME (codes OGR d'appellation) puis l'API ESCO** — seule correspondance officielle trouvée ; couverture 71 % des fiches à la vérification 1.1 (86,4 % en 1.7, avec toutes les appellations du CSV ; 85,0 % avec une exposition), les autres n'affichent pas d'exposition à l'IA — alternative écartée : rapprochement ISCO par libellé (non officiel) — à valider : non.
- **OIT 2025 : scores lus dans le tableau A1 de la version web officielle (webapps.ilo.org), pas dans le PDF** — tableau HTML propre (427 professions), pas de XLSX officiel — alternative écartée : site GitHub de l'auteur (non institutionnel) — à valider : non.
- **CIDJ : lecture page par page (≤ 1 requête/s, robots.txt respecté, URL citée pour chaque salaire)** comme source n° 1 du salaire de début, faute de l'Onisep — aucune licence ouverte affichée ; on ne reprend que des faits ponctuels avec citation — à valider : **oui** (droit de réutilisation).
- **INSEE 2024, salaire net moyen en EQTP par profession (PCS), privé : candidat de secours, non utilisé sans accord** — c'est une moyenne, pas une médiane ni un salaire de début, absente de l'ordre de `CLAUDE.md` §5 ; et il faut une table ROME ↔ PCS (bloquée) — à valider : **oui**.
- **Licence de la nomenclature FAP (DARES) : traitée comme Licence Ouverte**, bien que data.gouv.fr indique « non précisée » — usage habituel de la DARES ; on ne publie que des libellés — à valider : oui.
- **Import ROME en Python (`scripts/data/import_rome.py`), enchaîné par `scripts/data/run_all.py` (`npm run data`)** — réutilise `telecharger.py` ; une liste d'étapes dans `run_all.py` accueillera les imports suivants — alternative écartée : un script npm par import — à valider : non.
- **Test de schéma des données en Vitest + zod (`tests/donnees-rome.test.ts`, schéma partagé `src/lib/donnees/schema-rome.ts`), donc dans `npm run check`** — le même schéma typera le chargement des données dans l'application ; le JSON est lu par `fs` (pas d'`import`) pour ne pas faire typer 11 Mo à TypeScript — alternative écartée : pytest (deuxième outil de test, schéma non réutilisable côté produit) — à valider : non.
- **ROME découpé en deux fichiers : `metiers.json` (11,2 Mo) et `metiers_competences.json` (savoir-faire et savoirs, 12,3 Mo), même clé `code_rome`** — d'un seul tenant le fichier pesait 23,5 Mo (> 20 Mo) ; les savoir-faire en font plus de la moitié et ne servent qu'au rapprochement, pas à l'affichage courant ; JSON compact, une fiche par ligne (diffs lisibles) — alternatives écartées : référentiel de compétences normalisé par code OGR (illisible sans jointure), suppression des codes OGR (perte de la clé stable) — à valider : non.
- **Appellations prises dans le CSV `unix_referentiel_appellation` (14 330), pas dans le JSON (11 932)** — le JSON omet l'appellation principale et les appellations peu usitées, et 308 fiches y sont vides ; ordre : principale d'abord, puis alphabétique ; les « peu usitées » sont gardées avec `peu_usitee: true` — à valider : non.
- **Textes ROME gardés tels quels, en deux formes : texte intégral du JSON (`definition`, `acces_metier`) et phrases du CSV (`definition_phrases`, `acces_metier_phrases`)** — dans le JSON, les phrases à puces sont collées sans ponctuation (« …infractions environnementales Assure le respect… ») ; les phrases permettent un affichage en liste ; seules retouches : espaces de début et de fin, et `''` → `'` dans le CSV (artefact d'échappement) — à valider : non.
- **Indicateurs officiels O/N convertis en booléens, vide → `null` (« non renseigné »), jamais `false` par défaut ; `coeur_metier: "Principale"` → `true`** — un champ vide (ex. emploi réglementé : 21 % des fiches) ne doit pas se lire « non réglementé » — à valider : non.

- **Type de formation normalisé en 21 codes (BTS, BUT, LICENCE, LICENCE_PRO, CPGE, DE, ECOLE_INGENIEUR…), déduit du préfixe de la première mention (« BTSA - … », « D.E … »), puis de la catégorie Parcoursup** — `Types de formation` est une liste de catégories de recherche (« Etudes de santé,Licence » pour une L.AS), pas un diplôme ; le libellé d'origine reste dans `types_parcoursup` et `mentions` ; contrôle bloquant si plus de 1 % tombe en « AUTRE » (0 aujourd'hui) — alternative écartée : premier élément de `Types de formation` — à valider : non.

- **Textes Parcoursup : espaces multiples réduits à une seule** (« Formations  des écoles d'ingénieurs ») — retouche typographique sans effet sur le sens ; listes découpées sur les virgules non suivies d'une espace, un morceau en minuscule restant attaché au précédent (« Administrateur systèmes,réseaux et cybersécurité ») — à valider : non.
- **Table de passage ROME → FAP 2021 : PDF officiel DARES diffusé par France Travail (page « Méthode » du site BMO), lu par `pdftotext`, au lieu d'un rapprochement par libellés** — c'est la table de référence, accessible sans défi anti-robot ; la lecture est contrôlée (532 codes ROME V3 retrouvés, FAP connues) — alternative écartée : rapprochement par libellés et domaines (prévu en 1.1, moins fiable, inutile) — à valider : non.

- **Plusieurs métiers BMO pour une fiche (selon la qualification) : étiquette « emploi cadre » du ROME → cadre ; intitulé « Technicien » → technicien ; « Chef d'équipe », « agent de maîtrise », « contremaître » → maîtrise ; sinon employé ou ouvrier qualifié (qualifications 3 et 6) ; confiance moyenne ; pas de départage → faible, aucune valeur** — le Bilan mène à des formations qualifiantes : le métier BMO qualifié est le plus représentatif ; précision mesurée 83 % sur les liens moyens — alternatives écartées : somme des métiers BMO candidats (mélange cadres et ouvriers peu qualifiés), métier BMO au plus grand nombre de projets (favorise les peu qualifiés) — à valider : oui (règle « ouvrier qualifié »).

- **Exposition à l'IA : niveau affiché repris des qualificatifs de l'OIT (tableau 5 du WP 140) : « Not Exposed », « Minimal Exposure » et « Gradient 1 » (low exposure) → faible ; « Gradient 2 » (moderate exposure) → modérée ; « Gradient 3 » (significant) et « Gradient 4 » (highest exposure) → élevée** — aucun seuil inventé : l'OIT qualifie elle-même chaque catégorie — alternatives écartées : seuils sur le score moyen (arbitraires), « Gradient 1 » en modérée (l'OIT le dit « low exposure ») — à valider : non.
- **ROME → ISCO-08 par les appellations (code OGR) de la table officielle ESCO ↔ ROME, puis l'API ESCO ; ISCO principal d'une fiche = ISCO du lien le plus fort de son appellation principale (son intitulé) quand elle est reliée (1 247 fiches) ; sinon celui que relient le plus d'appellations, en ne gardant que les liens forts (exactMatch, closeMatch) s'il y en a ; départage : nombre d'exactMatch, plus petit code** — l'intitulé est ce que le parent lit (la règle « majorité » seule donnait « médecin spécialiste » pour J1102 Médecin généraliste et « aide de cuisine » pour le commis) ; à défaut, majorité des appellations = ce que recouvre la fiche ; tous les ISCO restent dans `passage_rome_isco.json` (réutilisable pour les salaires, 1.6) — alternatives écartées : moyenne des scores des ISCO (mélange, chiffre absent de la source), ISCO le plus exposé (alarmiste) — à valider : non.
- **Exposition d'une fiche = celle de son ISCO principal ; si plusieurs ISCO de même rang donnent des niveaux différents, la fiche est marquée `concordance: false`, le niveau reste celui de l'ISCO principal** — le moteur ou l'écran pourra choisir de ne pas afficher l'IA pour ces fiches — alternative écartée : retirer d'office ces fiches (perte de couverture) — à valider : oui.

- **Niveau d'études minimum = plus bas niveau d'accès cité par le texte ROME (« sans diplôme » compris), codé en `bac_plus` (-2 sans diplôme, -1 avant le bac, 0 bac, N bac + N) ; diplôme cité sans niveau (DE, titre pro) → niveau européen RNCP du même domaine** — c'est ce que le moteur compare aux années d'études acceptées — alternatives écartées : niveau « habituel » (pas de règle sûre pour le dégager du texte), niveau RNCP seul (les diplômes de docteur sont NIV7) — à valider : non.
